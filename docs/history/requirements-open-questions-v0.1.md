## 一、协议、订阅与节点

### Q-PROTOCOL-001 第一版协议范围与既有代码基线

**来源：** C09、C117。

**问题：** C09 只列出 VMess、VLESS、Trojan、Shadowsocks、Hysteria2，但 C117 又要求以既有 parser 和 sing-box 映射为基线；既有代码还包含 TUIC。需要避免“沿用基线”被理解成继续支持 TUIC。

**选项：**

- A：第一版严格只支持 C09 的五种协议；既有代码只作为这五种协议字段映射的参考。
- B：第一版同时保留既有代码支持的 TUIC。

**建议结论：选择 A。**

正式需求应明确：第一版协议集合只有 VMess、VLESS、Trojan、Shadowsocks、Hysteria2；TUIC 及其他协议不支持。C117 所称“既有代码基线”只适用于这五种协议内部的字段和传输组合。

**状态：待确认。**

---

### Q-SUB-001 订阅中部分节点无效时的处理

**来源：** C09、C57、C164、C165、R01～R03。

**问题：** 一个订阅可能同时包含不支持协议、格式错误节点和有效节点。当前文档只明确了“没有有效节点时失败”和“重复 name 时整次失败”，没有定义部分失败能否继续预览和导入。错误处理还会影响节点删除及级联删除安全。

**选项：**

- A：不支持的协议可以跳过并在预览中报告；任何属于五种支持协议但解析或校验失败的节点，都使本次刷新整体失败；重复 name 仍整体失败。
- B：所有无效或不支持节点都跳过，只要至少剩一个有效节点就允许确认导入。
- C：出现任意不支持或无效节点都使整次刷新失败。

**建议结论：选择 A。**

这样既允许机场订阅混有其他协议，又避免原有受支持节点因一次解析异常被误判为删除并触发级联。刷新失败时原数据完全不变；跳过的不支持协议需要显示数量、协议和可识别的节点名，但不得显示凭据。

**状态：待确认。**

---

### Q-SUB-002 Filter/Exclude 的准确语义

**来源：** C55、C111。

**问题：** 尚未定义匹配字段、大小写、多关键词关系以及 Filter/Exclude 同时命中时的优先级。

**建议结论：**

- 只匹配节点 `name`；
- 忽略大小写；
- 关键词支持逗号或换行分隔，保存时去除首尾空白和空项；
- 多个 Filter 关键词采用 OR，命中任意一个即保留；Filter 为空表示不过滤；
- 多个 Exclude 关键词采用 OR，命中任意一个即排除；
- 同时命中 Filter 和 Exclude 时，Exclude 优先。

**状态：待确认。**

---

### Q-SUB-003 订阅节点能否人工编辑

**来源：** C08、C57～C59、C109～C119。

**问题：** 文档允许维护全局节点，但没有明确订阅产生的节点是否允许像自建节点一样人工编辑。如果允许，下一次刷新可能覆盖人工修改，节点来源也会变得不清晰。

**选项：**

- A：订阅节点只读，只能通过刷新或删除订阅更新；自建节点允许人工编辑。
- B：允许编辑订阅节点，但刷新时以订阅内容覆盖人工修改。
- C：编辑订阅节点后自动转为自建节点，与原订阅解除关系。

**建议结论：选择 A。**

页面应显示节点来源；订阅节点允许查看、检测、加入出站池和删除其所属订阅，但不允许直接修改协议参数。

**状态：待确认。**

---

### Q-SUB-004 订阅节点 name 的匹配规则

**来源：** C164。

**问题：** C164 规定只按 name 匹配，但没有明确大小写、首尾空白和 Unicode 规范化规则。

**建议结论：**

- parser 先去除 name 首尾空白；去除后为空则节点无效；
- 刷新匹配采用区分大小写的完整字符串相等；
- 不做 Unicode 规范化、地区别名或模糊匹配；
- 同一订阅内按上述规范化结果检查重复 name；
- 不同订阅之间允许同名，因为节点身份仍由订阅和内部 ID 区分。

**状态：待确认。**

---

### Q-NODE-001 全局节点合法性与启动阻断

**来源：** C11、C60、C68、C160、R05、R11。

**问题：** 所有全局节点都会写入 sing-box 配置，因此一个未被任何出站引用的错误节点也可能导致完整配置检查失败，阻止系统启动。

**选项：**

- A：节点只有通过协议字段校验并能够生成该版本支持的 sing-box 配置片段后才能保存或导入；启动时仍对完整配置执行最终检查。
- B：允许保存无效节点，生成配置时跳过无效节点。
- C：允许保存并写入，直到启动检查时报错。

**建议结论：选择 A。**

B 与“全部全局节点写入配置”不一致；C 会让无关节点阻断整个网关且错误发现过晚。订阅刷新应保持事务性：支持协议节点中任一节点无法通过校验时，本次刷新不产生可确认结果。

**状态：待确认。**

## 二、健康检测与故障切换

### Q-HEALTH-001 人工检测是否影响自动状态机

**来源：** C22、C23、C90、C157、R14。

**问题：** C90 说人工检测更新状态和显示；C157 又限定全节点不可用判断只使用自动检测结果。如果共用唯一一份最近健康结果，人工检测会间接改变自动状态机。

**选项：**

- A：人工检测更新页面展示结果，但不参与连续失败计数、全节点不可用计时或自动切换判断。
- B：人工检测更新统一健康结果，并允许影响全节点不可用计时。

**建议结论：选择 A。**

运行时至少区分“最近任意检测结果”和“最近自动状态机可采用的检测结果”。页面可以显示人工检测结果及其来源；自动状态机只采用控制循环产生的结果。

**状态：待确认。**

---

### Q-HEALTH-002 全节点连续不可用的准确判定

**来源：** C23、C94～C96、C157、C159。

**问题：** 尚未定义 unknown、checking、不同时间产生的旧结果以及计时起点如何参与“全部节点连续不可用 300 秒”。

**建议结论：**

1. 只有已被 route 引用且正处于 Emergency 的自动出站才可能开始全不可用计时；
2. 一次自动故障池完整扫描结束后，该池全部节点结果均为 unavailable，计时从该批次完成时开始；
3. unknown 不等于 unavailable，因此不能开始计时；
4. checking 不覆盖上次结果，但计时判断只在检测批次完成后的串行处理阶段更新；
5. 后续完整池扫描仍然全部 unavailable 时继续计时；
6. 任一自动检测结果恢复为 available 时立即清零；
7. 页面人工检测不开始、延续或清除该计时；
8. 达到等待时间后，在控制循环下一次处理该状态时重启整个 sing-box。

**状态：待确认。**

---

### Q-HEALTH-003 相同节点检测结果的复用范围

**来源：** C65、C148、C151、C153、C158。

**问题：** 相同节点可能被多个自动出站使用，但“单次结果可以共享”没有说明共享的时间范围。

**选项：**

- A：同一个控制循环任务周期内，同一节点最多实际检测一次；当前节点检测和各故障池扫描可以复用该结果。跨任务周期必须重新检测。
- B：只在同一个检测批次内复用，不同出站池即使处于同一周期也重新检测。
- C：在结果未超过某个有效期时跨周期复用。

**建议结论：选择 A。**

复用检测结果不等于共享出站状态：连续失败次数、当前节点、Emergency 状态和全不可用计时仍按出站分别维护。

**状态：待确认。**

---

### Q-FAILOVER-001 节点切换后的失败计数

**来源：** C83、C84、C92、C101、C151。

**问题：** 连续失败次数按出站维护，但没有规定从普通节点切到 Emergency、再切到另一个普通节点时是否清零。若不清零，新节点会继承旧节点的失败次数。

**选项：**

- A：任何已经确认成功的当前节点切换，都清零该出站的连续失败次数。
- B：失败次数绑定节点保存，切回同一节点时恢复旧计数。
- C：只在当前节点检测成功或 sing-box 重启时清零。

**建议结论：选择 A。**

只有 Clash API 已确认切换成功后才清零；切换失败不修改当前节点和计数。故障池扫描结果本身仍不增加或清零连续失败次数。

**状态：待确认。**

---

### Q-FAILOVER-002 Selector 热切换失败的处理

**来源：** C26～C28、C66、C107、C153、C166。

**问题：** 文档描述了切换成功路径，没有定义 Clash API 超时、拒绝或目标不存在时的状态。

**建议结论：**

- 只有 Clash API 明确返回成功后，ProxyHub 才更新内存当前节点和状态；
- 从故障普通节点切 Emergency 失败属于关键恢复失败：记录关键事件并立即重启 sing-box；重启后按既定启动规则让已生效自动出站从 Emergency 初始化；
- 从 Emergency 恢复普通候选节点失败：保持 Emergency，记录关键事件，下一个周期重新扫描并重试；
- 手动出站人工切换失败：保持原选择，页面返回失败，不修改数据库中的人工当前节点；
- 如果失败原因是 sing-box 已退出，统一交由本轮串行生命周期处理执行重启，不并发启动第二个恢复动作。

**状态：待确认。**

## 三、运行生命周期与出站行为

### Q-RUNTIME-001 停止状态能否人工检测节点

**来源：** C38、C61、C63、C124、C160。

**问题：** 真实 URL 检测依赖正在运行的 sing-box Clash API，但页面人工检测的可用状态没有明确写出。

**选项：**

- A：人工节点检测仅在 sing-box running 时可用；stopped 或未安装时禁用并提示原因。
- B：stopped 时为了检测临时启动 sing-box 或临时检测进程。

**建议结论：选择 A。**

第一版不为人工检测建立临时进程或临时配置生命周期。

**状态：待确认。**

---

### Q-RUNTIME-002 空数据库首次启动行为

**来源：** C60、C103、C130、C149、C152。

**问题：** ProxyHub 重启后原则上自动启动 sing-box，但全新安装可能没有二进制，也可能有二进制但尚无有效 route。

**选项：**

- A：只有二进制存在且数据库至少包含一条能够生成有效配置的 route 时才自动生成配置并启动；否则 Web 正常运行、期望状态为 stopped。
- B：只要二进制存在，即使没有 route 也启动空业务配置。

**建议结论：选择 A。**

“ProxyHub 重启后不保留上次人工停止状态并自动启动”的规则，仅在具备二进制和至少一条有效 route 时适用。首次配置完成后由用户人工点击启动。

**状态：待确认。**

---

### Q-RUNTIME-003 不同重启场景是否重新生成配置

**来源：** C60、C100～C107、C124、C139。

**问题：** “启动”和“重启”在不同场景中出现，但没有明确哪些路径重新生成并检查配置，哪些路径直接使用已经加载的正式配置。

**建议结论：**

- 人工点击 Start：从数据库生成临时配置、检查、替换正式配置并启动；
- 人工点击 Restart：停止后执行与 Start 相同的生成和检查流程；检查失败则保持 stopped；
- 全节点不可用触发的自动重启：直接使用当前正式配置重启，不重新读取数据库生成配置；
- 意外退出后的守护重启：直接使用当前正式配置重启；
- ProxyHub 程序自身启动：满足 Q-RUNTIME-002 前置条件时，从数据库重新生成、检查并启动；
- 所有实际 sing-box 重启成功后都按 C101 重置运行时状态机。

**状态：待确认。**

---

### Q-OUTBOUND-001 手动出站“第一个节点”的定义

**来源：** C54、C74、C75。

**问题：** 手动出站不使用优先级，但当前节点被移除时需要回退到“第一个节点”，因此仍然需要稳定的节点列表顺序。

**选项：**

- A：手动出站保留稳定的加入顺序，但不提供排序功能；当前节点被移除时选择最早加入且仍存在的节点。
- B：手动出站也允许用户排序，但该顺序只用于回退，不称为优先级。
- C：不保存顺序，按节点数据库 ID 最小者回退。

**建议结论：选择 A。**

首次加入的节点仍成为当前节点；后续人工选择持久化。加入顺序只解决展示和确定性回退，不参与健康选择或自动切换。

**状态：待确认。**

## 四、认证与升级可靠性

### Q-AUTH-001 公网管理页面的最低认证边界

**来源：** C120、C121、C129、C141、C150、N17。

**问题：** 管理页面可能通过公网访问且默认密码为空。N17 排除企业级防御，但仍需定义第一版最低认证行为，否则不同实现可能遗漏移动端、内部接口或会话失效。

**建议结论：**

- 密码非空时，桌面页面、移动页面、全部内部 API 和日志下载都必须认证；
- 密码只保存安全哈希，不保存或记录明文；
- 提供登录和退出；
- 修改用户名或密码后立即使既有登录会话失效，用户重新登录；

### Q-UPGRADE-001 sing-box 升级失败保护

**来源：** C127、C128、C131、R08、R10。

**问题：** “下载成功后直接替换”没有说明下载中断、文件损坏或新二进制不可执行时如何保护旧版本。

**建议结论：**

1. 下载到同一文件系统内的临时文件；
2. 验证下载完成、资产架构正确、文件可执行，并能读取合法版本；
3. 验证成功后原子替换正式二进制；
4. 任一步失败都保留原二进制并报告失败；
5. 替换成功后仍不自动启动，由用户人工启动；
6. 第一版不要求保存多版本、自动回滚历史版本或后台自动升级。

## 五、确认后需要补充的场景

以下不是新的待决问题，而是正式需求冻结前必须形成的可验收场景：

1. 全新安装、没有 sing-box、没有 route；
2. 完成首次配置并人工启动；
3. 自动出站普通节点正常运行；
4. 当前普通节点达到失败阈值并切换 Emergency；
5. 下一周期扫描后恢复普通候选节点；
6. Emergency 和全部 Candidate 均不可用，等待后重启；
7. Selector 切换 API 失败；
8. 多个自动出站同一周期同时故障；
9. 人工停止、修改结构配置、重新启动；
10. sing-box 意外退出并由守护逻辑恢复；
11. 订阅正常新增、修改和删除；
12. 订阅包含不支持协议或无效的支持协议节点；
13. 订阅删除 Emergency 或最后一个 Candidate 并触发级联；
14. 手动出站人工切换、切换失败及重启恢复；
15. 修改检测设置和修改登录凭据。

上述问题全部确认后，将结论转写为原子化的 `REQ-*` 正式需求，并为这些场景编写对应验收标准。
