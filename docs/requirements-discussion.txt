ProxyHub 个人版需求讨论清单
==========================

文档状态：需求讨论中，尚未进入软件设计与开发
更新日期：2026-08-26

使用方法
--------

1. 每项都有固定编号，后续讨论和修改均引用编号。
2. 可以这样回复：
   - C03：确认
   - Q87：确认先切应急节点，再并发检测普通候选节点
   - N04：我仍然需要，移到待讨论
   - 新增：希望支持……
3. “已明确”表示已经从当前场景中确认，但仍可修改。
4. “待讨论”不代表一定要实现，只表示它会影响产品行为或设计边界。
5. 本文档只记录需求，不决定使用 Flask、SQLite 等具体技术。


一、核心目标（已明确）
----------------------

C01. ProxyHub 是供单人使用、自行部署的本地代理网关管理工具。

C02. 系统接收机场订阅节点和用户自建节点，并将它们转换为本地代理入站，供本机或其他设备使用。

C03. 系统需要持续检测节点健康状态，并在当前节点不可用时自动恢复相关出站的代理能力。

C04. 故障恢复采用两阶段策略：先快速切换到明确指定的稳定应急节点，再查找并切换到优先级更高的可用普通节点。

C05. 项目只需要满足个人真实使用场景，不以公共服务、企业部署、多用户平台或通用代理管理平台为目标。


二、节点来源与协议（已明确）
----------------------------

C06. 支持添加和刷新机场订阅。

C07. 请求机场订阅 URL 时，需要使用 Clash 客户端兼容的请求方式，以获取 Clash 格式的代理订阅。

C08. 支持用户手动添加和维护自建节点。

C09. 支持以下远程节点/出站协议：
     - VMess
     - VLESS
     - Trojan
     - Shadowsocks
     - Hysteria2
     - TUIC

C10. Shadowsocks 节点需要支持 obfs。

C11. 订阅刷新后，节点配置需要能够用于生成 sing-box 出站。


三、本地入站（已明确）
----------------------

C12. 支持将远程节点转换为本地 HTTP 入站。

C13. 支持本地 SOCKS 入站。

C14. 支持本地 Mixed 入站，即同一监听端口兼容 HTTP 和 SOCKS。

C15. 支持本地 Shadowsocks 入站。

C16. 支持本地 VMess 入站。


四、节点健康检测（已明确）
--------------------------

C17. 系统需要在后台定时执行节点健康检测，无需用户手动触发。

C18. 节点检测包含 TCP 检测，用于确认节点服务器地址和端口是否可连接。

C19. 节点检测包含 URL 检测，用于确认节点能够实际转发代理流量。

C20. URL 检测流量必须真实经过被检测节点，不能直接使用本机网络访问测试 URL。

C21. 健康检测不能继续采用 v1 的全局单线程逐节点串行方式，需要在控制资源占用的前提下并发检测多个节点。

C22. 节点延迟、最近检测时间、失败原因、连续失败次数等健康状态属于临时运行状态，不保存到数据库；程序重启后重新检测。

C23. 系统需要区分至少以下运行时健康状态：未检测、检测中、可用、不可用。


五、自动故障切换（已明确）
--------------------------

C24. 每个需要自动切换的出站都有一个当前使用节点。

C25. 当前节点被判定不可用时，不先等待普通候选节点扫描完成。

C26. 当前节点被判定不可用后，系统首先切换到事先明确指定的应急节点，以尽快恢复代理流量。

C27. 切换到应急节点后，系统有限并发检测该出站池的全部节点，再根据完整检测结果选择优先级最高的可用普通节点。

C28. 找到符合条件的可用普通节点后，系统自动从应急节点切换到该普通节点。

C153. 自动出站当前节点达到连续失败阈值后，准确顺序为：先通过 Clash API 立即热切换到应急节点；随后有限并发检测该出站池全部节点，包括应急节点；检测批次完成后，从可用普通候选节点中选择优先级最高的节点热切换。没有可用普通候选节点时保持应急节点。

C157. 控制循环持续从内存读取每个已被 route 引用的自动出站全部节点的最近健康结果。如果某个这类出站的全部节点连续达到配置的等待时间（默认 300 秒）都处于不可用状态，则重启整个 sing-box。该判断本身不主动发起检测，只使用当前节点检测、故障池扫描和全量检测已经写入内存的结果；任一节点结果恢复为可用时，该出站的连续全不可用计时清零。未被 route 引用的自动出站不触发自动切换或重启。

C158. 当前节点检测、故障池扫描、全量节点检测和进程守护都由同一个串行控制循环调度，任意时刻只运行一个检测批次。检测批次内部有限并发，批次结束后单线程控制逻辑才继续处理状态、切换或重启。

C29. 应急节点是自动出站节点池中的一个明确成员，由独立标记指定，并在前端特殊显示；不能再隐含为“节点池中优先级最高的节点”。

C30. 应急节点的职责与普通候选节点优先级相互独立。应急节点不参与普通候选节点的 1 至 N 优先级排序。


六、整体运行方式（已明确）
--------------------------

C31. 新版本只使用 sing-box，不再组合 sslocal、Xray 和 sing-box 多个代理引擎。

C32. 只使用一个常驻 sing-box 进程承载全部本地入站、远程节点和切换能力。

C33. 系统需要作为长期运行的服务工作，而不是只在用户打开页面时运行。


七、入站、出站与路由模型（已明确）
----------------------------------

C34. 系统允许同时创建和运行多个入站。

C35. 每个入站独立定义监听协议、监听地址、监听端口和该协议需要的认证参数。例如：HTTP 1080、SOCKS 1081，以及后续任意数量的其他入站。

C36. 系统允许创建多个出站。

C37. 普通代理出站至少包含一个远程节点。

C38. 手动出站可以只包含一个节点；此时不会自动故障切换，但该节点仍参加全局定时健康检测。不另外建立“固定节点”出站类型。

C39. 自动类型的普通代理出站包含普通候选节点和应急节点，并按已确认的健康检测与故障切换规则运行。

C40. 系统提供 direct 类型的特殊出站。direct 出站不包含远程节点，流量直接访问目标地址。

C41. 系统允许创建任意数量的 route。

C42. 每条 route 只表达一个简单映射：一个入站指向一个出站。

C43. 路由关系中不再额外引入“服务”这一层业务概念。sing-box 的运行状态属于整个系统；节点选择和故障切换状态属于出站。

C44. 如果多个 route 指向同一个出站，它们将共享该出站的当前节点和故障切换状态。

C45. 一个入站最多只能绑定一条 route；入站也可以暂时不绑定 route。因此 route 数量始终小于或等于入站数量。

C46. 同一个出站允许被零条、一条或多条 route 复用。

C47. 当多条 route 复用同一个出站时，这些 route 对应的入站共享该出站的当前节点、应急节点、候选节点优先级和故障切换状态。

C147. 每条 route 必须同时引用一个入站和一个出站，不允许缺少任一端。删除入站时，所有引用该入站的 route 一并删除。

C155. 未绑定 route 的入站只保存在数据库中，不写入 sing-box 配置。删除出站时，所有引用该出站的 route 一并删除。

本节原 Q01 至 Q08、Q55 和 Q56 已全部确认。


八、出站模式、候选节点与优先级
------------------------------

C48. 出站分为三种业务类型：自动出站、手动出站和 direct 出站。

C49. 自动出站的同一个节点池中至少包含一个普通候选节点和一个被特殊标记的应急节点。普通候选节点由用户排序，应急节点不参与该排序。

C50. 自动出站中普通候选节点的优先级由用户手工排序决定。保存顺序后，系统自动生成连续且唯一的 1 至 N 优先级。

C51. 系统不根据延迟或其他指标自动调整普通候选节点优先级。

C52. 自动出站不允许用户临时手动切换当前节点，也不需要“锁定当前节点”功能；当前节点完全由自动策略管理。

C53. 自动出站需要扫描节点池时，有限并发检测整个池；检测批次完成后，从可用普通候选节点中选择人工优先级最高的节点，不按延迟排序。

C54. 手动出站由用户纯手工选择当前节点，不使用节点优先级，也不执行自动切换。

C55. 添加机场订阅时，前端支持直接输入订阅 URL，并配置 Filter 包含关键词和 Exclude 排除关键词。

C56. 添加自建节点时，前端同时支持逐项输入协议参数和粘贴协议 URI 两种方式。

C57. 只有 sing-box 已停止时才能刷新订阅。系统请求、解析并经过 Filter/Exclude 得到候选结果后，先计算与当前订阅节点的差异，并在前端显示新增、修改、删除的节点数量和明细；只有用户确认后才导入。确认删除订阅节点时，同时从所有引用它的出站节点池中删除对应成员。取消确认时不修改任何数据。

C154. 订阅刷新删除节点后，如果某个手动出站节点池变为空，或者某个自动出站缺少应急节点或普通候选节点，则直接删除整个出站；同时删除所有引用该出站的 route。订阅差异确认界面应一并显示将被级联删除的出站和 route。

C58. 自动出站和手动出站的节点都由用户从全局节点列表中手工添加或移除。

C59. 订阅刷新，以及节点、入站、出站或 route 的新增、修改、删除，只有 sing-box 已停止时才允许执行。修改直接保存到数据库，不设置“待应用更改”状态。手动出站切换当前节点和自动出站普通节点优先级调整不改变 sing-box 配置，允许在运行时直接生效。

C60. 不提供独立的“应用配置”操作。用户点击启动 sing-box 时，系统根据当前数据库重新生成完整配置，执行配置检查，检查成功后写入正式配置文件并启动；检查失败时保持停止状态。

C61. sing-box 运行期间禁止结构配置修改，因此健康检测、故障切换、数据库结构和当前加载配置使用同一节点集合。停止期间保存的结构修改在下一次启动时写入配置；停止状态不运行节点检测。

C62. 自动出站每次随 sing-box 重新启动时，初始先选择自己的应急节点，然后有限并发检测整个出站池，并按人工优先级选择最高的可用普通候选节点热切换。

C63. 手动出站允许包含多个节点，并允许用户通过页面随时切换当前节点。手动出站的节点参加后台周期健康检测，但检测结果只供查看，不触发自动切换。

C64. 后台只有一个串行控制循环，sing-box 进程守护、自动出站状态处理和节点检测调度均在该循环内执行；不建立独立的守护线程或多个调度器。

C65. 控制循环按配置的基础触发周期运行（默认 15 秒）。该周期同时用于 sing-box 进程守护、自动切换状态处理和全量检测到期判断。对于已被 route 引用且未处于应急节点的自动出站，本轮有限并发检测其当前节点；相同出站被多条 route 复用时只检测一次，相同节点被多个出站使用时复用同一次检测结果。

C66. 如果某个自动出站当前节点达到连续失败阈值，控制循环立即发起该出站整个节点池的有限并发检测；完成全部结果处理和必要切换后，控制循环才继续执行其他工作。

C159. 如果已被 route 引用的自动出站当前正在使用应急节点，则每个基础触发周期都有限并发检测该出站整个节点池。检测批次完成后，如果存在可用普通候选节点，立即热切换到其中人工优先级最高的节点；如果没有，则继续保持应急节点。

C67. 只有当本轮所有被使用的自动出站当前节点都可用、本轮没有执行应急出站池扫描或故障切换扫描，并且距离上次全量检测已达到配置的全量检测周期时，才有限并发检测全局节点列表中的所有节点。全量检测只更新内存健康结果和前端显示，不触发自动出站择优或节点切换。当自动故障恢复工作与全量检测同时到期时，优先故障恢复，全量检测延后到后续空闲周期。

C68. 启动时生成配置，将全局节点列表中的全部节点写入 sing-box 配置，即使某些节点未被任何出站池引用，以便对所有节点执行真实 URL 检测。本文统一称这类节点为“未被出站池引用的全局节点”，不使用“隐藏节点”这一名称。

C160. sing-box 配置中，每个全局节点都作为可被 Clash API 检测的独立节点出站写入；ProxyHub 的手动或自动出站池对应 sing-box 中引用指定节点的 selector 组。因此节点无论是否被出站池引用，都可以执行 URL 检测。

C148. 节点检测是控制循环中唯一允许有限并发的工作。控制循环等待当前检测批次全部完成并处理结果后再继续，不允许两个检测批次重叠运行。

C73. 新建普通出站时，默认类型为手动出站。

C74. 手动出站没有应急节点，也没有节点优先级。首次向新建手动出站加入节点时，第一个节点成为当前使用节点。

C75. 用户在手动出站中切换节点后，该节点成为出站保存的当前节点；下次启动或重启 sing-box 后继续使用这个人工选择。若该节点已被移出出站，则使用出站节点列表中的第一个节点。

C76. 将手动出站切换为自动出站时，必须明确指定一个应急节点，并为普通候选节点手工排序；缺少应急节点时不允许保存为自动出站。

C77. 自动出站的应急节点始终是独立配置，不使用“把最高优先级普通节点自动视为应急节点”的长期规则或旧数据兼容规则。

本节原 Q09 至 Q16、Q57 至 Q63 已全部确认。


八-A、数据持久化边界（已明确）
--------------------------------

C69. 数据库保持简单，主要业务实体为：订阅、节点、入站、出站和 route。

C70. 不为了新版本大幅重构现有基础数据库模型；只增加实现已确认需求所必需的字段或关联，例如出站模式、节点顺序和明确的应急节点。

C71. 节点健康结果、延迟、连续失败次数、检测调度状态和自动切换状态不写入数据库。

C72. 出站与多个节点之间的具体物理存储方式属于后续数据模型设计问题；可以使用必要的关联表或出站配置字段，但不增加新的用户业务概念。


九、故障判定（主体已明确）
--------------------------

C80. 每次节点健康检测先执行 TCP 检测。TCP 失败时立即结束本次检测，不再执行 URL 检测，本次结果记为失败。

C81. TCP 检测成功后继续执行 URL 检测。节点最终是否健康以 URL 检测结果为准；TCP 检测主要用于快速排除明显不可连接的节点。

C82. TCP 失败和 URL 失败在故障滤波中使用相同的失败语义，不根据失败类型设置不同的切换阈值。

C83. 当前节点单次检测失败不会立即触发故障切换。系统累计连续失败次数，达到用户可配置的阈值后，才将当前节点判定为不可用并切换到应急节点。

C84. 当前节点在达到失败阈值前任意一次检测成功，连续失败次数清零。

C85. 自动出站当前节点的检测周期直接使用单一控制循环的基础触发周期，不再另设一项“当前节点周期”配置。

C86. 当前节点检测失败但尚未达到阈值时，在下一轮配置的当前节点检测周期继续检测，不设置单独的快速复查周期。

C87. TCP 检测超时时间和 URL 检测超时时间分别配置。

C88. 所有节点共用一个全局测试 URL，不为订阅、节点或出站分别配置测试 URL。

C89. URL 检测通过 sing-box Clash API 的 delay 接口执行。Clash API 响应 HTTP 状态码为 2xx，且返回的 delay 大于 0 时，本次 URL 检测成功；其他情况均视为失败。当前 Clash API 成功响应实际为 HTTP 200。该规则写在程序中，不作为用户设置项。

C90. 只有当前节点故障后触发的出站池扫描可以自动选择并切换普通候选节点；全量检测和页面人工检测即使发现更高优先级可用节点，也只更新状态和显示，不触发切换。

C91. 节点切换后暂不设置最短保持时间。

C92. 故障滤波只用于把当前节点判定为不可用；不用于延迟从应急节点恢复到可用普通节点。

本节原 Q17 至 Q26、Q64 已全部确认。

十、应急节点与全节点不可用（主体已明确）
--------------------------------------

C93. 每个自动出站只允许指定一个应急节点，不建立多级应急节点列表。

C94. 自动出站进入应急节点后，如果应急节点和全部普通候选节点都不可用，则保持选择应急节点，不继续切换到其他已知不可用节点。

C95. 自动出站全部节点不可用时，不停止指向该出站的入站，也不删除或修改 route；系统保持现有配置并进入等待恢复状态。

C96. 等待恢复状态使用可配置的延迟时间。延迟结束后，系统重启整个 sing-box 进程。

C100. 因全节点不可用而全局重启完成后，所有自动出站重新执行初始选择流程；手动出站恢复其保存的人工选择。

C101. 每次 sing-box 重启都视为整个运行时状态机重新初始化。重启后清空健康检测结果、连续失败次数、全节点不可用状态、检测与恢复计时器以及其他故障切换临时变量，然后从初始状态重新开始检测和选择。

C102. 不为多个出站分别维护待执行的重启队列，也不增加额外的全局重启冷却或指数退避机制。某次重启一旦发生，其他出站此前积累的触发状态随状态机一起清空。

C97. 节点切换、全部节点不可用、sing-box 启动或重启、配置生成和升级等关键操作需要写入专门的关键事件日志等级，供前端只展示重要信息。

C98. 第一版不实现消息推送接口、推送 URL、Token 或具体平台集成。后续如增加推送，由日志模块处理上述专用等级，在记录日志的同时转发推送。

十一、启动、重启与状态恢复（已明确）
----------------------------------

C103. ProxyHub 程序每次启动后，都自动根据已保存数据生成并加载完整 sing-box 配置，然后启动 sing-box。上一个 ProxyHub 进程中的人工停止状态不跨 ProxyHub 重启保留。不存在启用/禁用字段：每条现存 route 都生效；只有被 route 引用的入站写入配置，未绑定 route 的入站不生效。

C78. 自动出站的启动行为由 C62 确认；手动出站的启动和恢复行为由 C74、C75 确认。

C79. 只持久化手动出站由用户明确选择的当前节点。自动出站不持久化自动选择的运行节点，健康和延迟状态也不持久化。

C104. 单一后台控制循环同时承担 sing-box 进程守护。只有期望运行状态为 running、但实际进程意外退出时，控制循环才自动重新启动 sing-box。

C105. sing-box 运行时禁止订阅、节点、入站、出站或 route 的结构修改。用户先停止 sing-box，再直接修改数据库；下一次点击启动时按 C60 自动生成、检查和写入配置。不提供配置热重载或独立应用步骤。

C106. 因人工启动或重启、故障恢复或意外退出而启动 sing-box 后，都按 C101 完整重置运行时状态机。

C107. 运行期间只切换出站当前节点时，调用 sing-box Clash API 完成热切换，不重启 sing-box，也不重置其他出站的状态。

C108. sing-box 进程生命周期由 ProxyHub 统一管理；守护任务只负责本项目管理的这一个 sing-box 进程。

C149. ProxyHub 维护一个只存于内存的简单期望运行状态。人工启动设置为 running；人工停止和配置检查失败设置为 stopped。期望状态为 stopped 时，控制循环不得自动启动 sing-box。ProxyHub 程序本身重启后，重新按 C103 自动启动 sing-box。

C151. 同一个节点被多个自动出站使用时，单次 TCP/URL 检测结果可以共享，但连续失败次数、当前节点和故障切换状态仍按出站分别维护。

十五、最低可靠性与实现简化边界（主体已明确）
------------------------------------------

R01. 手动刷新订阅时，请求失败只在前端显示失败提示；原订阅节点、已保存配置和当前运行配置均不改变。

R02. 订阅内容为空、格式错误或没有解析出有效节点时，不产生可确认的导入结果，不清空原节点；前端显示失败原因。

R03. 订阅解析成功时按 C57 显示新增、修改和删除预览，用户确认后才导入。

R04. 保留一份上次可用的 sing-box 配置，用于人工排错或恢复，但配置检查失败后不自动继续运行或恢复旧配置。

R05. 基本校验节点必填字段和端口范围，避免明显错误节点破坏完整配置，不建立大型通用校验框架。

R06. 日志不输出完整订阅 URL、UUID、密码、密钥等凭据。

R07. 订阅请求直接使用所选 HTTP 客户端的默认 HTTPS 证书验证行为，不编写自定义证书、安全策略或“忽略证书”逻辑。

R08. 除节点检测批次内部并发外，配置生成、sing-box 启停、升级等改变状态的操作都在单进程内串行执行；不支持多 Web worker，也不建立跨进程锁体系。

R09. 删除订阅、节点、入站、出站或 route 等不可逆操作前，页面进行简单确认。

R13. 人工删除订阅或节点时，使用与订阅刷新删除相同的级联规则：先展示所有受影响的出站和 route；用户确认后删除节点关联，删除因此失去全部节点的手动出站，删除因此失去应急节点或普通候选节点的自动出站，并删除引用这些出站的 route。数据库外键负责可直接表达的级联，业务层只补充“出站失效后删除出站”的规则。

R10. sing-box 启动、配置生成或其他操作失败时，只需记录足够排错的后端日志。前端显示简单失败提示和关键事件，不提供完整日志浏览；用户可下载日志文件排错。不建立复杂的结构化错误模型和专项错误页面。

R11. 点击启动时如果新生成的配置检查失败，sing-box 保持停止，等待用户查看日志、修改数据库配置并再次人工启动；不自动恢复或启动旧配置。

R12. 后台只有一个串行控制循环；节点检测批次内部允许使用数量受限的并发，控制循环等待批次完成后再继续，解决 v1 逐节点串行导致检测过慢的问题，同时避免多个后台状态机并行运行。

R14. 页面人工检查与周期检查共用同一个全局检测状态和有限并发执行器。同一时间只运行一个检测批次；已有批次运行时，新的人工检查返回“检测进行中”。不保存任务历史，不建立任务队列，前端只显示当前批次进度和结果。

本节 R01 至 R14 已全部确认。单次检测批次的有限并发数量见配置项章节。
